# Deploying SecureSphere to Render

This puts SecureSphere online at a public HTTPS address such as
`https://securesphere.onrender.com`, using Render's free tier:

- **One web service.** A Docker container runs the API and serves the React app from the
  same origin, which keeps the HttpOnly session cookies and CSRF protection working
  unchanged.
- **One PostgreSQL database**, reachable only from inside Render.

Everything is described in [`render.yaml`](render.yaml), so Render creates it all from your
GitHub repository in one go.

> **Free-tier limits** (check [render.com/pricing](https://render.com/pricing) for current
> details): the free web service sleeps after about 15 minutes without traffic, and the next
> visit takes roughly a minute to wake it. Free PostgreSQL databases expire after a limited
> period (about 30 days at the time of writing). This is fine for a demo or project
> presentation; upgrade both to paid plans for anything long-lived.

---

## Step 1: Push the code to GitHub

The Blueprint deploys from your repository, so make sure your latest commit is pushed:

```bash
git push
```

## Step 2: Create a Render account

1. Go to <https://dashboard.render.com/register> and sign up **with GitHub**.
2. When asked, grant Render access to the **SecureSphere** repository (you can choose
   "Only select repositories").

## Step 3: Create the Blueprint

1. In the Render Dashboard, click **New** → **Blueprint**.
2. Select the **Ctrl-Joy/SecureSphere** repository and click **Connect**.
3. Give the Blueprint a name, e.g. `securesphere`. Render shows what it will create:
   - **securesphere**: web service (Docker, free)
   - **securesphere-db**: PostgreSQL (free)

## Step 4: Fill in the secret values

Render asks for the three values marked `sync: false` in `render.yaml`. These are never
stored in the repository:

| Variable | What to enter |
|---|---|
| `SS_BOOTSTRAP_ADMIN_EMAIL` | The email you will sign in with as administrator. Use a real-looking address such as `you@gmail.com`; reserved domains like `.test` are rejected. |
| `SS_BOOTSTRAP_ADMIN_NAME` | Your name |
| `SS_BOOTSTRAP_ADMIN_PASSWORD` | A strong password: at least 12 characters, not containing your email or name. A passphrase of four or more random words works well. |

`SS_SECRET_KEY` is generated by Render automatically, and the database URL is wired up
automatically.

Click **Deploy Blueprint** (or **Apply**).

## Step 5: Wait for the first deploy (about 5–10 minutes)

Open the **securesphere** service and watch the **Logs** tab. A successful start shows:

```
Applying database migrations...
INFO  [alembic.runtime.migration] Running upgrade  -> 0001, initial schema
bootstrap-admin: administrator created: you@gmail.com
INFO:     Uvicorn running on http://0.0.0.0:10000
```

When the status turns **Live**, open the URL at the top of the service page
(`https://securesphere-xxxx.onrender.com`) and sign in with your admin email and password.

**Then secure it:** go to **securesphere → Environment**, delete
`SS_BOOTSTRAP_ADMIN_PASSWORD`, and save. The account already exists, and the bootstrap
never changes an existing account, so the variable is no longer needed and should not stay
stored.

## Step 6 (optional): Enable password-reset emails

The Blueprint starts with `SS_MAIL_BACKEND=none`. Password-reset requests are accepted, but no
email is sent. To send real emails, create a free account with an SMTP provider (for example
Brevo, Resend or SendGrid), then in **securesphere → Environment** set:

| Variable | Value |
|---|---|
| `SS_MAIL_BACKEND` | `smtp` |
| `SS_SMTP_HOST` | your provider's SMTP host, e.g. `smtp-relay.brevo.com` |
| `SS_SMTP_PORT` | `587` |
| `SS_SMTP_USERNAME` | from your provider |
| `SS_SMTP_PASSWORD` | from your provider (an SMTP key, not your account password) |
| `SS_MAIL_FROM` | a sender address your provider has verified, e.g. `SecureSphere <you@gmail.com>` |

Saving environment changes redeploys the service automatically.

## Step 7: Check that it works

1. Open the site: the landing page loads over **HTTPS**.
2. Register a second account, sign in, and open **Dashboard**, **Security lab** and
   **Account settings**.
3. Sign in as the admin and open **Security monitoring**: you should see the registration
   and sign-in events from step 2.
4. Optional: in your browser's developer tools, the cookie is named `__Host-ss_session`
   with **HttpOnly**, **Secure** and **SameSite=Lax** set.

## Updating the live site

Every push to `main` redeploys automatically (`autoDeploy: true`). Migrations run on each
start, so schema changes apply themselves.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Deploy fails with `SS_SECRET_KEY must be...` | The secret was not generated. Add `SS_SECRET_KEY` in Environment with a random value of 40+ characters. |
| Logs show `bootstrap-admin: password rejected` | The admin password did not meet the policy. Set a stronger `SS_BOOTSTRAP_ADMIN_PASSWORD` and redeploy (**Manual Deploy** → **Deploy latest commit**). |
| `bootstrap-admin: invalid email` | Use a normal email domain; `.test`, `.local` and similar reserved names are rejected. |
| First visit takes a minute | Normal on the free plan: the service was asleep. |
| "Your session has ended" right after signing in | You are on `http://`; free Render URLs are always `https://`. Use the `https://` address. |
| Database expired | Free databases are time-limited. Create a new one or upgrade the plan, then redeploy. |

## How this deployment is secured

- **Database:** reachable only from inside Render (`ipAllowList: []`). The connection string
  never leaves Render's environment settings.
- **Secrets:** the secret key is generated by Render. The admin password is entered once in
  the dashboard and deleted after first use.
- **Startup checks:** the app refuses to start in production with a weak secret, a
  non-PostgreSQL database, insecure cookies or development email.
- **Browser security:** HTTPS with HSTS, `__Host-` Secure cookies, and a strict
  Content-Security-Policy that allows no inline scripts and only same-origin fonts.
- **Container:** runs as a non-root user from a minimal Python image.

> Note on IP-based rate limits: behind Render's proxy, client IPs come from forwarded
> headers. Per-email limits and account lockout do not depend on IPs and stay fully
> effective.
